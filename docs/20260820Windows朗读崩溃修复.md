# Windows 朗读崩溃修复

## 问题与范围

- 复现入口：Windows 版“开示”页面点击“朗读”。
- 现象：`flutter_tts` 从非平台线程向 `flutter_tts` channel 发送消息，可能导致消息丢失或进程崩溃。
- 根因：Windows 原生播放完成回调运行在线程池线程，却直接调用了 Flutter `MethodChannel`；SAPI 路径还在该线程直接完成 `MethodResult`。
- 后续现象：朗读可以自然结束，但开示页仍显示停止按钮。`flutter_tts` 的 channel 为静态单例，多个 `FlutterTts` 实例会互相覆盖原生事件处理器，使当前页面的 `completionHandler` 可能收不到通知。
- 二次定位：线程切换修复把完成消息投递到了 Flutter View 的子窗口，却把消息处理器注册在应用顶层窗口；消息未经过顶层窗口过程，导致 `speak.onComplete` 和等待中的 `speak()` Future 都没有完成。
- 实机复测：改投顶层窗口后仍未恢复按钮，说明不能依赖 Flutter Runner 将自定义窗口消息转交给插件代理。完成消息需要由插件自身拥有的消息窗口接收。
- 范围：只修复 Windows 原生实现，不改变应用侧 `TtsTools` API 和其他平台行为。

## 技术方案

1. 将 `flutter_tts 4.2.0` 固定为仓库内的 path 依赖，避免修改 Pub 缓存造成修复不可复现。
2. 后台播放完成回调只通过 `PostMessageW` 向应用窗口投递自定义消息。
3. 使用 Flutter Windows 顶层窗口过程代理，在平台线程中调用 `speak.onComplete` 并完成等待中的 `MethodResult`。
4. 朗读被取消后忽略迟到的完成消息，防止同时触发取消和完成回调。
5. 同时修复 MediaPlayer 和 SAPI 两条 Windows 编译路径。
6. 应用侧以等待中的 `speak()` Future 完成作为可靠兜底，并保证完成回调最多执行一次；页面状态不再只依赖可能被其他实例覆盖的 channel handler。
7. 不再依赖 Flutter View、应用顶层窗口和 Runner 的消息转发；插件在注册线程创建仅用于收消息的 message-only window。
8. MediaPlayer/SAPI 后台完成回调只向该窗口 `PostMessageW`，其窗口过程运行在创建窗口的平台线程，再安全触发 `speak.onComplete` 和完成 `speak()` Future。

## 回滚

将 `pubspec.yaml` 的 `flutter_tts` 恢复为发布版本依赖并删除项目内副本即可。项目内副本保留了上游包的完整代码，修改集中在 Windows 插件实现。

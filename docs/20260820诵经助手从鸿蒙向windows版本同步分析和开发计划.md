## 一、结论

当前不合并两个代码仓库，也不改变现有项目结构。本阶段采用“功能级人工移植”的方式，把鸿蒙版中已经实现、而 Windows/Android 共用项目中缺失或明显较弱的业务功能，同步到 `/Users/yangxuehui/Documents/dev/Android/gongke`。

该方案总体可行。Windows 和 Android 共用 Flutter/Dart 业务代码，大部分新增能力只需实现一次，但必须分别在 Windows、Android 上验证。鸿蒙项目中的 OHOS 插件、ArkTS 卡片、鸿蒙专用数据库和文件选择器不能直接复制到标准 Flutter 项目。

本次明确不处理：

- 隐私确认界面。
- 启动失败界面。
- 鸿蒙桌面卡片及其刷新、快照、深链能力。
- 项目合并、Git 仓库合并或分支历史重写。

建议同步范围分为三组：

1. 十念法与木鱼节奏体系。
2. 开示/法语功能第二版，包括收藏、完成、评论、排序、分享、导入导出等。
3. 少量通用稳定性改进，包括拜忏流程和功课保存保护。

预计开发量为 **7～13 人日**，不包含需求调整、UI 大改、Windows 桌面小组件，也不包含本次明确排除的隐私确认和启动失败界面。

## 3.5 开示 JSON 导入导出第二版

现有项目已有基础导入能力，鸿蒙版增加了更完整的版本化格式、冲突处理和安全校验，建议同步为统一的 `TipFileCodec`。

### 需要同步的能力

- 带版本号的 JSON schema。
- 兼容 macOS/Swift Codable 日期格式。
- 导入导出时保持书籍和记录稳定 ID。
- UTF-8、JSON 结构、schema、Base64 图片完整性校验。
- 单个文件最大 10 MiB。
- Base64 解码后的单张图片最大 2 MiB。
- 批量导入前展示预览。
- 单次最多选择 15 个文件。
- 冲突处理策略：跳过、更新现有、另存为新书。
- 每个文件使用独立数据库事务，单个文件失败不影响其他文件。
- 展示成功、跳过、失败的明细和原因。
- 支持 JSON 导出。
- 增加导出后再次导入的往返一致性测试。

### 导入冲突的判定和推荐交互

“导入冲突”是指导入文件中的书籍或记录，与本机已有数据拥有相同的稳定标识，例如相同的 `sourceId`、`productId`，或同一本书下相同的 `jsonId`。这通常发生在重复导入同一文件、导入同一书籍的新版本，或另一台设备修改后再次导入。

推荐在导入预览中显示冲突数量，并提供以下三种处理方式：

1. **跳过（默认且推荐）**：保留本机数据，不导入冲突项。适合误操作或无法判断版本新旧的情况，数据风险最低。
2. **更新现有**：用导入文件更新标题、正文、标签、图片等内容字段；本机已有的收藏状态、完成状态、评论和用户排序默认保留。导入文件明确包含更新版本时可使用此项。
3. **另存为新书**：为导入内容生成新的书籍 ID 和记录 ID，两份内容同时保留。适合用户希望对照两个版本的情况，但可能形成重复内容。

交互建议：默认选中“跳过”；支持“对本次全部冲突使用此选择”；执行前显示将跳过、更新和新建的数量；选择“更新现有”时再次提示“内容会更新，个人收藏、完成状态和评论会保留”。任何策略都应在单文件事务中完成，失败时回滚该文件的全部修改。

## 七、技术实施方案

### 7.1 分层迁移顺序

```text
数据库 schema v2 与迁移测试
        ↓
开示 JSON 编解码、导入导出服务
        ↓
每日开示、收藏/完成/评论/排序业务服务
        ↓
开示页面和首页预览 UI
        ↓
十念法模型、持久化和音频控制器
        ↓
十念法管理页面和念圣号页面
        ↓
拜忏与功课保存稳定性改进
        ↓
Windows + Android 完整回归
```

该顺序可以避免 UI 先依赖不稳定数据结构，也便于每阶段独立提交和回退。

### 7.2 数据库升级策略

1. 对现有 v1 数据库制作脱敏测试副本。
2. 在 Drift 表定义中新增字段和唯一约束。
3. 编写 v1 → v2 migration：先加字段、回填稳定 ID 和排序值、清理重复，再建唯一约束。
4. 使用标准项目依赖重新生成代码。
5. 验证新安装和旧数据库升级两条路径。
6. 在 Windows、Android 上分别验证数据条数、收藏状态、日期和排序未丢失。

### 7.3 功能开关与兼容

- 数据库完成升级前，不暴露依赖新字段的 UI。
- 导入逻辑同时识别旧格式和 v2 格式；导出统一使用 v2。
- 新木鱼节奏未配置时回退到普通模式，保证旧用户行为不变。
- 新增设置项必须有默认值，旧版 SharedPreferences 中不存在键时不能报错。

### 7.4 Git 和提交策略

- 按产品要求只维护 `main` 一条主线，不创建或推送额外功能分支。
- 开始前确认当前分支为 `main`，工作区干净，并记录 HEAD；发现名为“右键助手”等额外分支时不要继续向其推送。
- 一项业务能力一个或少量聚焦提交，禁止把依赖升级、数据库迁移和大面积 UI 改动混在同一提交。
- 每个阶段通过测试后再进入下一阶段。
- 每次提交前检查 `git diff`，每个阶段验证通过后再提交到 `main`；推送由用户确认或按用户在 Windows 环境中的明确授权执行。
- 文档确认前不修改业务代码。

### 12.1 接手时的第一轮检查

在 Windows 的 `/Users/...` 路径不可用，应以 Windows 机器上的实际仓库路径为准。先执行并记录：

```powershell
git status --short --branch
git rev-parse HEAD
git branch --all
git remote -v
git config --show-origin --get user.name
git config --show-origin --get user.email
where.exe flutter
flutter --version
flutter doctor -v
```

检查要求：

- 当前分支必须是 `main`，不要创建或推送“右键助手”等额外分支。
- 本文分析时 Windows/Android 基线为 `6c87577`；如果 Windows 环境 HEAD 已变化，不要强行 reset，应先分析新增提交并把实际 HEAD 写回本文。
- 工作区如有未提交修改，先判断是否为用户已有工作；不得覆盖、清理或纳入本任务提交。
- Git 的 `user.name` 是提交作者显示名，GitHub 归属还取决于提交邮箱是否被账号验证以及 push 使用的认证账号。不要仅因显示名称不同而修改全局 Git 配置；如需调整，只改本仓库 local 配置并先让用户确认。
- 项目只保留 `main` 主线。GitHub 页面出现“某名称 had recent pushes”通常表示同名分支刚被推送，不代表仓库里出现了另一个 GitHub 用户。
